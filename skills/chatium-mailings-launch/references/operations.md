# Тест, запуск, отчёт и ошибки

## Проверяемый черновик

До внешней отправки должны быть известны: аккаунт, mailingId, актуальный revision контента, каналы, аудитория, время и предел разрешения пользователя. Превью, состав аудитории и summary достаточны для обсуждения запуска; сначала подготовь их, затем уточняй недостающую авторизацию. Если запуск уже разрешён для этого варианта, продолжай без повторного вопроса.

```ts
const ready = await sdk.prepareMailing(ctx, { mailingId });
return {
  id: ready.id,
  status: ready.status,
  audience: ready.audienceTitle,
  channels: ready.transportSnapshots,
  coverage: ready.coverage,
  error: ready.error,
};
```

prepare проверяет обязательный контент, переменные, аудиторию и каналы. Не проверяет рендер в почтовом клиенте и не доказывает, что Telegram примет Markdown. Пустой сегмент отклоняется. До запуска держи audience в коллекции с понятным именем; её состав может меняться, это динамическая ссылка, а не зафиксированный список.

## Отправка теста

Выбери contactIds из listTestRecipients; для email допускается ручной адрес. Передавай только согласованных тестовых получателей. Предел — 50 выбранных адресов/контактов на запрос; несколько каналов могут дать больше фактических сообщений.

```ts
const doc = await sdk.getMailingContent(ctx, mailingId);
const { test } = await sdk.sendMailingTest(ctx, {
  id: mailingId,
  key: "review-v1-to-owner",
  expectedRevision: doc.revision,
  contactIds: [chosenContactId],
  emails: [],
});
return { testId: test.id, sourceMailingId: mailingId, pending: test.pending };
```

Для собственного email: contactIds:[], emails:[confirmedEmail]. Имя пользователя в чате не всегда определяет его адрес, используй профиль/CRM или уточни.

Запомни ключ до вызова. На сетевом таймауте повтори **тот же** payload и key. Если контент изменился и нужен новый тест, используй новый key. Повтор старого ключа не пересылает новую версию; другие адреса с тем же ключом отклоняются. Это защита от случайного расширения теста.

```ts
const { test } = await sdk.getMailingTest(ctx, {
  id: testId,
  sourceMailingId: mailingId,
});
return test;
```

Сначала тест может быть pending; повторяй чтение с короткими интервалами, пока выполняется работа. Когда достигнут конечный результат или явная ошибка — останови polling. Если исход остаётся неизвестным после нескольких проверок, сообщи это и сохрани ID, не создавай автоматическую повторную отправку.

Читай **каждый** test.results:

- status:pending/sending — работа ещё выполняется;
- status:accepted — Sender принял задание, доставка этим не доказана;
- status:error + error — ошибка постановки/отправки;
- status:unknown — исход неоднозначен, сначала диагностика;
- delivery.status:failed + response — последующая ошибка транспорта, включая Telegram `can't parse entities`;
- delivery.status:delivered — есть подтверждение;
- diagnosticUnavailable:true — источник диагностик недоступен, это не отсутствие ошибок.

test.status:completed означает окончание обработки теста, а не обязательный успех всех получателей. История `listMailingTests` сохраняется после завершения основной рассылки; `getCurrentMailingTest` ищет именно текущую конфигурацию, поэтому может вернуть null при наличии старых тестов.

## Основной запуск

```ts
// Только когда пользователь разрешил этот запуск.
const started = await sdk.startMailing(ctx, { mailingId });
return { id: started.id, status: started.status, runAt: started.runAt };
```

Для будущего времени передай ISO с явной зоной, например `2026-12-01T10:00:00+03:00` после сверки даты с пользователем. Примерная дата из документа не является выбором времени. Если сохранено scheduleMode:scheduled, пропуск runAt сохраняет установленное расписание: сначала прочитай `getMailing` и сопоставь с задачей.

startMailing идемпотентен для уже запущенной записи: повтор не создаёт новый тираж. Для отменённой/ошибочной рассылки нельзя считать возвращённый прежний статус новым стартом. Уточни конкретную причину, подготовь новый черновик только в разрешённом объёме. Не обходи защиту массовым клонированием.

В группе сначала прочитай groupMembers, зафиксируй разрешённые ID и запусти каждый отдельно. Если один запуск неуспешен, отчитайся по каждому; операция не является общей транзакцией. Общая аудитория не означает общую дедупликацию между каналами/дочерними.

## Диагностика

1. `getMailing(id)`: status,error,preparationProgress,queueFailure,batchState. «Завершена» отражает обработку; не приравнивай к 100% доставке.
2. `getMailingStats(id)`: stats.total/channels/reasons, stats.delivery и trackingDebug. Недоступный источник не заменяй нулями в выводах.
3. `listMailingDeliveries({mailingId,status:'error',offset:0,pageSize:20})`: ошибки могут появиться после принятия Sender. Для каждой нужной записи `getMailingDeliveryErrors({mailingId,deliveryId})`, где deliveryId взят из ответа, а не собран вручную.
4. Покажи человеку ошибку транспорта и связанное сообщение, предложи точечное исправление. Исходный успешный приём в очередь сохраняется в истории даже при последующей ошибке.

Telegram Bot API не даёт боту отдельного подтверждения доставки на устройство/прочтения. Подтверждённая отправка не должна отображаться как «не доставлено». В других каналах учитывай реальные события, не переноси ограничения Telegram на email/MAX/ВК. Переход по ссылке не подменяет доставку или открытие. При неизвестном статусе показывай «нет подтверждения», не «0 доставлено».

`getMailingGroupStats` суммирует сообщения дочерних и досылок, исключая тесты. Это не уникальные люди: один получатель может встретиться в нескольких каналах. Если deliveredKnown/openedKnown false или есть unavailableRuns, показывай соответствующее ограничение; положительный known в смешанной группе ещё не доказывает покрытие всех транспортов.

## Остановка рассылки

1. Установи аккаунт и нужную отправку из разговора, ссылки или `listMailings`. Для записи с `isGroup` или `displayRun` сначала определи ID по разделу «Группа и досылки» ниже. Если совпадений несколько, уточни выбор; не останавливай все рассылки аккаунта по общему слову «рассылка». Явная просьба остановить выбранную отправку уже разрешает это действие.
2. Прочитай `getMailing(ctx, mailingId)`. Отменяются состояния `scheduled`, `preparing`, `sending`, `error`. Для `draft` отправка ещё не началась, для `completed` уже завершилась; SDK может вернуть их без изменения — не называй такой результат выполненной отменой.
3. Вызови `stopMailing(ctx, {mailingId})` для каждой выбранной отправки. После таймаута сначала перечитай состояние; при необходимости повторяй остановку того же ID. Не вызывай `startMailing` и не создавай новый тираж для проверки отмены.

```ts
const sdk = await import('@mailings/sdk');
const stopped = await sdk.stopMailing(ctx, { mailingId });
const current = await sdk.getMailing(ctx, stopped.id);
return {
  id: current.id,
  status: current.status,
  phase: current.batchState?.phase ?? null,
  accepted: current.acceptedCount,
  errors: current.errorCount,
  error: current.error,
};
```

4. Проверь возвращённое состояние повторным чтением. `status:'cancelled'` прекращает дальнейшую подготовку/постановку сообщений. У batch-отправки `batchState.phase:'cancelling'` означает, что отмена очереди ещё выполняется; дождись `phase:'finished'`, повторяя чтение с короткими интервалами. При ошибке транспорта или затянувшейся отмене сообщи «отмена запрошена, завершение очереди пока не подтверждено» и сохрани ID для дальнейшей проверки. Не выдавай один успешный вызов за завершение всей фоновой работы.
5. Покажи статус каждого ID и известные результаты отправки. Уже доставленные сообщения отозвать нельзя; сообщения, отправлявшиеся в момент отмены, ещё могут дойти. Отмена не обнуляет счётчики и не меняет записанные исходы доставки. Это окончательная отмена тиража, а не пауза с гарантированным продолжением.

### Группа и досылки

`stopMailing` не принимает ID группы. Прочитай `getMailingGroup(ctx, groupId)`, выбери разрешённые `groupMembers` и останавливай конкретные отправки. Если пользователь просит остановить один транспорт, остальные дочерние не затрагивай; при остановке всей группы обработай всех её детей и отчитайся отдельно об ошибках каждого вызова.

Список и группа могут показывать семью отправок: `member.id` — исходная рассылка, а `member.displayRun?.id` — текущая отправка, в том числе досылка. Проверь оба известных ID через `getMailing` и отменяй подходящие по статусу в пределах выбранной семьи, убирая дубликаты. После отмены перечитай группу/список: следующим `displayRun` может стать другая активная досылка; её также обработай, если запрошена остановка всей семьи. Дождись окончания `cancelling`, прежде чем считать семью остановленной.

`runsSummary.active` включает и тесты, а `displayRun` не перечисляет всю историю. Для проверки тестов используй `listMailingTests`; не включай их в операцию без соответствующего запроса. Если доступный SDK не позволяет установить оставшиеся активные ID или чтение недоступно, перечисли подтверждённо остановленные отправки и явно укажи, что полная остановка группы не подтверждена. Не обращайся к внутренним `/plugin/...` маршрутам или таблицам ради обхода публичного SDK.

## Архив и удаление

`archiveMailing` меняет видимость, а не останавливает отправку; активные отправки архивировать нельзя. По просьбе архивировать группу вызывай её root ID, а не удаляй детей. `deleteMailing` применим только к черновику. Просьба остановить не подразумевает архивирование или удаление истории.
