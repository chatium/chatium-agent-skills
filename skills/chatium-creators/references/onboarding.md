# Кабинет и безопасное подключение

## Первый вход

1. `getCreatorContext(ctx)` возвращает текущий аккаунт/пользователя, подключённый профиль
   либо `connected:false`, а также точные ссылки в `links`. Используй их, не собирай домен
   Store по памяти: кластер и preview могут различаться.
2. Для знакомства покажи `links.introduction`. Регистрация открывается через
   `links.registration`; платформа проводит обычный вход. Не проси пароль, cookie или OAuth-токен.
3. Обязательны публичное имя, slug и контактный e-mail. Имя до 120 символов; slug —
   3–40 строчных латинских букв/цифр/дефисов, первая буква; e-mail будет публичным.
   Помоги придумать название и описание, но спроси недостающий контакт у человека.
4. После регистрации человек владеет профилем в центральном Store. Вызови
   `beginCreatorConnection(ctx)` из исходного аккаунта, покажи `approvalUrl`.
   Это ссылка на 15 минут. Владелец видит аккаунт и пользователя, выбирает свой кабинет
   и явно подтверждает доступ. Регистрация и подтверждение — отдельные действия.
5. После подтверждения перечитай `getCreatorContext`. Результат должен содержать ожидаемые
   аккаунт и профиль. Только после этого начинай записи кабинета.

Если во время подтверждения профиля ещё нет, человек может создать его в новой вкладке,
затем обновить страницу подтверждения. Истёкшую ссылку заменяют новым вызовом begin;
ошибка/прошедшее время не означают, что доступ разрешён. Не опрашивай статус постоянно.

SDK регистрации профиля нет: нельзя безопасно назначать владельца центрального кабинета
по локальному userId другого аккаунта. Это обычная авторизация, а не недостаток прав агента.

## Что можно заполнить

`updateCreatorProfile` меняет публичное имя/slug/email/описание, сайт, Telegram, логотип,
ссылки поддержки, условий и политики. Передай только нужные поля, сохрани остальные.
Профиль публичен по своему URL; это не скрытый черновик. Для первого черновика не нужны
сайт и банковские реквизиты. Перед заявкой нужны заполненный профиль с описанием и оферта.

По `links.agreement` **реальный владелец** читает и принимает оферту. Обычное сохранение
профиля её не принимает. Агент не может поставить `acceptedAgreement` через SDK.

В кабинете также есть менеджеры, уведомления, заказы, финансы и реквизиты. Эти разделы
остаются ручными: не выдавай SDK карточек за API управления командой или выплатами.
Менеджер, приглашённый в кабинете, не получает подключение SDK автоматически.

## Несколько аккаунтов и отзыв

Подключение разрешает конкретному пользователю исходного аккаунта управлять всем
выбранным кабинетом — включая карточки, созданные из других подключённых аккаунтов.
Другие сотрудники того же аккаунта доступа не получают. У каждого — собственное
подтверждение владельцем. Требуется действующая системная роль Developer/Owner исходного
аккаунта при каждом вызове; роль креатора в Store не заменяет эту роль.

Владелец видит все связи через `links.connections` или настройки кабинета и может
немедленно отозвать любую. Сам агент может `disconnectCreatorAccount(ctx)` только для
своего текущего пользователя/аккаунта. Для переключения кабинета сначала отключи прежний
по поручению пользователя, затем получи новое подтверждение. Отзыв не удаляет карточки,
покупки, установленные приложения и ранее скачанные файлы.

Если владельца профиля сменили, старые подключения недействительны. Авторизация не
переносится копированием кода, ZIP или Git-ветки: учитываются реальные ID аккаунта и пользователя.
