# Доступ, покупки и ресурсы плагина через Store SDK

Настраивай тариф и опции в [редакторе карточки](commerce.md#условия-тарифа-и-опции-плагина).
Код плагина использует серверный `@store/sdk` в аккаунте установки. Методы с проверкой
caller плагина вызывай из его маршрутов, функций или jobs. Обычный `chatium exec`
из кода аккаунта подходит для диагностики по slug, но не даёт контекст плагина.

## Какую проверку выбрать

| Что проверяешь | Где и чем |
| --- | --- |
| Разрешения самого приложения на данные аккаунта | Проверь декларацию в исходниках плагина. Для доступного приложения каталога `getPluginInstallInfo(ctx, slug)` из кода аккаунта под Admin+ показывает полный список заявленных `permissions`. См. [установку](../../chatium-development/store-plugin-install.md). |
| Доступ аккаунта к платному плагину | `pluginUserApp` для пользовательских маршрутов; `checkPluginAccess(ctx)` из плагина для функций и jobs вне middleware. Для диагностики выбранного плагина в текущем аккаунте есть `checkPluginAccessBySlug(ctx, slug)` и `checkPluginAccessById(ctx, id)`, где `id` — числовой ID приложения платформы. |
| Лимит пользователей плагина | `pluginUserApp` дополнительно проверяет назначение доступа текущему пользователю, если для плагина включён лимит. См. [настройку лимита](commerce.md#лимит-пользователей-плагина). |
| Право пользователя на действие или конкретный объект | Проверь роль через `@app/auth` или разрешение через `@app/rbac`. Если право должно зависеть от рабочего места в аккаунте, у Permission есть `requiresSeat`. См. [RBAC](../../chatium-development/rbac.md). |
| Наличие функции по тарифу, число единиц опции или остаток ресурса | `getPluginOptionPurchases(ctx, { key })` из плагина. Для списания расходуемой опции используй `spendOptionResource`. |

В проверке доступа ориентируйся на `success`. Для бесплатного плагина возможен
`success: true` с `purchase: null`. Запись о заказе, установленный плагин и его
опубликованная карточка сами по себе не подтверждают право на платную функцию.
Рабочее место [владельца кабинета](onboarding.md#рабочее-место-и-привязка-аккаунта)
проверяется отдельно при публикации решения. Оно не выдаёт доступ покупателю.

### Маршрут и фоновая операция

Пример для плагина с объявленным разрешением `reports:run`. Применяй middleware ко
всем платным страницам и API плагина. Проверку роли или RBAC делай перед чтением
объекта или выполнением операции. В job отдельно проверь право аккаунта и полномочия
на саму фоновую задачу, заданные при её постановке.

```ts
import { requirePermission } from '@app/rbac'
import { AccessDeniedError } from '@app/errors'
import { checkPluginAccess, pluginUserApp } from '@store/sdk'

pluginUserApp.get('/reports/status', async ctx => {
  await requirePermission(ctx, 'reports:run')
  return { available: true }
})

// Вызывай из защищённой функции или job в коде плагина.
export async function requirePaidPluginAccess(ctx: app.Ctx) {
  const access = await checkPluginAccess(ctx)
  if (!access.success) {
    throw new AccessDeniedError('Нужен действующий доступ к плагину')
  }
}
```

`checkPluginAccess` проверяет доступ аккаунта. Если операция вызвана человеком
в обход `pluginUserApp`, проверь его права независимо. При отказе или ошибке
Store заверши защищённую операцию. Проверяй доступ заново при выполнении, включая
jobs, чтобы учесть окончание срока и отзыв доступа. Для собственного экрана
покупки есть `goToPaymentRequireScreen(ctx, slug)` для действия навигации и
`redirectToPaymentRequireScreen(ctx, slug)` для серверного редиректа.

## Читать и расходовать опции

`getPluginOptionPurchases` возвращает массив для текущего плагина и аккаунта.
Передай `key` или `optionId`. Без фильтра вернутся все его купленные опции.
По умолчанию выдаются действующие покупки. `showExpired: true` используй для
диагностики. У записи есть `option.id`, `option.key`, `option.type`, `value` и
`finishAt`. `null` в `finishAt` означает бессрочный доступ. У `subscription`
поле `value` хранит доступное количество единиц. У `resource` это остаток.

При поиске по ключу сверь `option.key` в ответе. Нераспознанный ключ в текущем
SDK может оставить запрос без фильтра. Пустой список подходящих записей означает
отсутствие действующей покупки, а исключение означает сбой чтения.

`calcOptionResource(ctx, { key })` и вариант с `optionId` возвращают суммарный `value`
при `success: true`.
Эта функция принимает также массив ключей или ID и сама не отсекает истёкшие
покупки. Для допуска к действующей квоте читай активные покупки через
`getPluginOptionPurchases`.

Пример ресурса `report_exports`, где один экспорт расходует одну единицу.
Вызови функцию после проверок доступа. Для одновременных операций организуй
единую последовательность действий по аккаунту и опции, как описано ниже.

```ts
import { getPluginOptionPurchases, spendOptionResource } from '@store/sdk'

const EXPORTS = 'report_exports'

export async function readExportQuota(ctx: app.Ctx) {
  const purchases = await getPluginOptionPurchases(ctx, { key: EXPORTS })
  return purchases.find(p => p.option.key === EXPORTS && p.option.type === 'resource')
}

export async function debitOneExport(ctx: app.Ctx) {
  const quota = await readExportQuota(ctx)
  if (!quota || (quota.value ?? 0) < 1) {
    throw new Error('Нет действующей квоты на экспорт')
  }

  const result = await spendOptionResource(ctx, { optionId: quota.option.id, value: 1 })
  if (!result?.success) {
    throw new Error(result?.message || 'Списание экспорта не подтверждено')
  }
}
```

- `spendOptionResource` изменяет данные. Передавай положительный расход из
  бизнес-операции, проверяй срок и остаток перед списанием. SDK не отсекает
  истёкшую покупку при списании и допускает отрицательный остаток. Для показа
  обновлённого остатка перечитай покупки после подтверждённого списания.
- Для строгой квоты сериализуй в плагине чтение и списание по аккаунту и ресурсу.
  Все пути списания должны пользоваться одной очередью или общей блокировкой
  через `runWithExclusiveLock` из `@app/sync`.
  Серия «прочитать → сравнить → списать» сама по себе не атомарна. Блокировка
  приложения упорядочивает его вызовы, но не делает внешние покупки и возвраты
  частью одной транзакции. Если бизнесу нужен строгий общий лимит, предусмотрите
  резервирование и сверку для этой модели.
- При повторной доставке события используй ID бизнес-операции. У `spendOptionResource`
  нет ключа идемпотентности. Если ответ не пришёл или операция прервалась между
  списанием и сохранением своего результата, проверь фактический расход перед
  повтором. Успешное списание само по себе не подтверждает выполнение экспорта.
- Массив ключей/ID в `spendOptionResource` задаёт порядок расхода. Выбирай его
  явно, например сначала срочный пакет. Несколько опций списываются по отдельности,
  поэтому при ошибке проверь каждую. Для новой интеграции начни с одной опции.

## Тарифы, расчёты и заказы из кода

Обычную покупку проводи через экран Store. Для собственной формы плагина
бери ID/slug тарифа из настроек приложения. Перед расчётом или созданием заказа
проверь тариф вызовом `getOfferInfo` и полномочия пользователя на покупку.
Операции покупки выполняй для согласованных условий в аккаунте покупателя.

| Метод | Когда использовать |
| --- | --- |
| `getOfferInfo(ctx, offerIdOrSlug)` | Из плагина прочитать свой тариф и `conditions`. При `success: false` обработать `message`. |
| `calcOrderResults(ctx, { params })` | Показать предварительную стоимость. Для обычного тарифа `params` содержит `offerId` или `offerSlug`, `positionsCount` и `optionsCounts`. Для одного пакета оба множителя равны `1`. Для перерасчёта подписной опции укажи `orderType: 'change_subscription'`. |
| `createOrder(ctx, params)` | Создать заказ по выбранному тарифу. Используй возвращённый `paymentLink` для перехода к оплате. Нулевой заказ может сразу выдать доступ. Перед показом функции снова проверь покупку или опцию по SDK. |
| `calcOptionsAccessPeriod(ctx, { key, newOptionsCount })` | Предварительный пересчёт срока действующей опции при изменении количества. Можно передать `optionId` вместо `key`. Поле результата называется `newFinisAt`. Если SDK вернул сообщение об отсутствующей опции или покупке, дата не подтверждает доступ. |
| `createOrderWithChangeSubscriptionOptions(ctx, { offerId, newOptionsCount })` | Запустить изменение количества подписной опции по подходящему тарифу. Сначала покажи расчёт. Обработай `paymentLink`, затем перечитай покупку. Для расходуемого ресурса используй обычный тариф пополнения. |
| `getAppPurchases(ctx, slug)` / `getOrdersByOffer(ctx, { offerIds, status })` | Диагностика покупок и заказов текущего аккаунта. Для истории по тарифам самого плагина есть `findAppOrders`. Держи чтение истории на сервере и проверяй права пользователя перед показом заказов. |

`createOrder` и изменение количества имеют побочные эффекты. Для проверки тарифа
без покупки используй чтение и расчёт. Для решений о доступе учитывай актуальный результат
проверки, а для опций после оплаты сверяй `value` и `finishAt`.

## Запросить отзыв в интерфейсе приложения

Из серверного кода установленного приложения вызови `getApplicationReviewStatus(ctx)`
из `@store/sdk`. При `status === 'available'` покажи сотруднику выбор оценки от 1 до 5,
поле комментария до 1000 символов и кнопку «Отправить отзыв». После явного нажатия
вызови `submitApplicationReview(ctx, {rating, comment})` в сессии этого сотрудника.
Комментарий необязателен. Store сам определяет приложение, сотрудника и аккаунт.

При `submitted` скрой форму и покажи сообщение о модерации. При `already-submitted`
следующая отправка возможна с `nextReviewAt` (ISO-строка). При `invalid` оставь
поля доступными для исправления. При `ineligible` скрой предложение оставить отзыв.
Методы доступны реальному сотруднику Staff+ в аккаунте клиента. Владелец решения и
аккаунт разработки исключены. После 24 часов новый отзыв проходит отдельную модерацию.
