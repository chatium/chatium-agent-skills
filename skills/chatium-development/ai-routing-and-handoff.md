# Маршрутизация и передача разговора

Несколько самостоятельных агентов могут быть привязаны к одному каналу Sender. Без включённого маршрута входящее сообщение может попасть всем привязанным агентам. Для клиентского канала явно настрой одного первого получателя. Если разговор уже ведётся, маршрутизатор прежде всего сохраняет текущего ответственного, если его не переопределяет более приоритетное правило или назначение. Правила, назначения и цепочки живут в аккаунте и **общие для Git-веток**.

## Простой маршрут через публичный SDK

Используй `@ai-agents/sdk/process`. Эти операции предназначены для серверного кода аккаунта с ролью Admin. Они не создают диалог и не отправляют сообщение.

1. После публикации найди фактический `agentId` по пути файла через `getPublishedAgentBySourcePath(ctx, sourcePath)` и точный ID канала Sender; привяжи агента через `linkAgentToChannel(ctx, { agentId, channelId })`, если связи ещё нет. Сверь возвращённые ветку и SHA-256 с целевой публикацией.
2. Прочитай `getProcessChannelRouting(ctx, channelId)`. Он возвращает `config` (или `null`) и `linkedAgentIds`. Сохрани `config.updatedAt`; для отсутствующей записи версия — пустая строка.
3. Для простого маршрута вызови `configureProcessChannelRouting` с `defaultAgentId`, `enabled: true`, `fallbackAction: 'default'`, `expectedUpdatedAt` и `sharedStateAcknowledged: true`. Последнее поле явно подтверждает, что изменение затронет все ветки. Метод откажет, если версия изменилась, агент не привязан или в канале есть пользовательские правила. Цепочки и назначения он не перенаправляет.
4. Снова прочитай состояние и вызови `dryRunProcessChannelRouting` с нормализованными контактами тестового клиента, который уже есть в CRM, но ещё не имеет цепочки. Проверь `mode: 'selected'` и ожидаемый `agentId`; отдельно проверь контакты другого тестового клиента с существующей CRM-цепочкой. Метод использует тот же поиск клиента, что и `redirectChainByContacts`, и не создаёт клиента, цепочку или назначение; возможна диагностическая метрика.

```ts
import {
  getProcessChannelRouting,
  configureProcessChannelRouting,
  dryRunProcessChannelRouting,
} from '@ai-agents/sdk/process'

const before = await getProcessChannelRouting(ctx, channelId)
if (!before.linkedAgentIds.includes(agentId)) throw new Error('Агент не привязан к каналу')
await configureProcessChannelRouting(ctx, {
  channelId,
  defaultAgentId: agentId,
  enabled: true,
  fallbackAction: 'default',
  expectedUpdatedAt: before.config?.updatedAt ?? '',
  sharedStateAcknowledged: true,
})
const result = await dryRunProcessChannelRouting(ctx, {
  channelId,
  contacts: [{ type: 'email', value: 'test-lead@example.com' }],
  text: 'Здравствуйте',
})
if (result.mode !== 'selected' || result.agentId !== agentId || result.reason !== 'default-agent') {
  throw new Error('Маршрут нового разговора не совпал')
}
```

Если CRM не находит клиента по контактам, dry-run возвращает `mode: 'unresolved'`: не подставляй собственный ключ и не считай маршрут проверенным. Для входящего без CRM-совпадения Sender использует идентификатор пользователя или чата, который нельзя восстановить по одним контактам. По той же причине dry-run по контактам не доказывает выбор старой цепочки, созданной с таким ключом; эти случаи проверь отдельным входящим сообщением на тестовом канале. Контакты для проверки должны быть тестовыми и иметь ту же нормализованную форму, что `customerContacts` во входящем событии Sender.

Это метод только для **простого адресата по умолчанию**. Если канал уже использует правила по тексту, A/B или особые назначения, разберись в действующей конфигурации и настрой её через административный интерфейс. Не удаляй правила ради успешного вызова SDK. `fallbackAction: 'ignore'` означает, что новое входящее без подходящего маршрута будет проигнорировано, а не передано другому агенту. Для отдельного запасного агента нужны явные правила. Наличие `config.enabled` само по себе не доказывает правильный выбор для конкретного клиента.

## Передача между агентами

Когда самостоятельный агент передаёт разговор после достижения конкретного результата, рекомендуемый путь — настроить в его `*.agent.json` встроенную цель:

```json
{
  "goal": {
    "type": "redirect2",
    "trigger": "Заявка подтверждена записью в CRM, и клиент согласился на разговор со специалистом",
    "redirectToAgentIds": ["<опубликованный agentId специалиста>"],
    "messageText": "Продолжи работу с подтверждённой заявкой; проверь её текущий статус в CRM."
  }
}
```

`redirectToAgentIds` содержит реальные ID опубликованных агентов, не пути файлов; после первой публикации найди их через `getPublishedAgentBySourcePath` и опубликуй обновлённый конфиг источника. Когда `trigger` действительно выполнен, агент вызывает встроенный `complete-goal`: платформа передаёт цепочку и отмечает цель достигнутой. Тул добавляется платформой, регистрировать его как custom tool не нужно. При нескольких разрешённых адресатах агент сначала вызывает `find-redirect-candidates`, выбирает подходящий ID из ответа и передаёт его в `complete-goal`; порядок кандидатов не означает приоритета. При пустом списке или неопределённости цель не завершай. Прежний тип цели `redirect` устарел.

`goal.messageText` задаётся заранее и не превращается в свежее резюме этого клиента. Сохраняй индивидуальные факты и статус в CRM/операционном источнике, обеспечь следующей роли доступ к ним и проверь реальную передачу на тестовой цепочке. Когда переключение инициирует серверный код вне хода агента либо нужно передать индивидуальное резюме прямо в сообщении следующей роли, используй `redirectChain(ctx, { fromAgentId, toAgentId, chainKey, messageText })`; если известны контакты клиента и ключ нужно разрешить через CRM — `redirectChainByContacts`. `messageText` должен кратко сообщить цель клиента, согласованные факты, обещанный следующий шаг и нерешённые вопросы без секретов и лишних персональных данных.

Оба способа используют один механизм перенаправления: новая цепочка получает идентичность клиента, CRM-связь, идентичность чата и серверный `chainContext` предыдущей цепочки; модель выбирается из конфига **нового** агента. Старый разговор помечается как перенаправленный, а дальнейшие сообщения по его ключу проходят через перенаправление. Параметр `copyChainParams` устарел и не управляет этим переносом. Передача не создаёт общую базу памяти всех агентов: бизнес-статус и документы сохраняй в CRM/операционном источнике, а следующему агенту предоставляй разрешённый доступ к ним.

Перед переключением проверь, что целевой агент опубликован и может работать с нужным каналом. После `complete-goal` или вызова SDK проверь фактическую целевую цепочку и тестовое входящее; для цели также проверь отметку достижения. Если передача отклонена или прервана, не объявляй её выполненной; оставь человеку понятный путь возврата. Не создавай автоматический круг взаимных перенаправлений.

## Preview и инструменты

Конфиг агента и custom tools читаются из текущей опубликованной ветки аккаунта. Инструмент, зарегистрированный через `@start/agent/tools`, доступен в preview этой ветки сразу после успешной публикации; в main он не появится до публикации в main. При этом маршруты каналов, назначения, история цепочек и пауза агента не изолированы по веткам. Для испытания используй отдельные тестовые контакты/ключи и не перенастраивай общий боевой канал без согласованного окна.
