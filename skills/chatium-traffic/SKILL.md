# Traffic SDK: выборки аккаунта

Используй серверный `import { queryAi } from '@traffic/sdk'`. Точное имя — `queryAi`, не `queryAI`. Функция принимает готовый ClickHouse SQL, а не вопрос на естественном языке, и возвращает `{ rows }`; ошибки выбрасывает исключением.

## Выполнение

1. Определи целевой аккаунт, период и единицу подсчёта: событие, просмотр, сессия, посетитель или пользователь. Аккаунт исходников traffic — не аккаунт клиента. Для внешнего запуска сверяй checkout и возвращённый `ctx.account`; не используй произвольный известный аккаунт как замену нужному.
2. Перед первой выборкой прочитай [контракт и схему](references/schema.md). Полный список колонок там снят через SDK. Если нужна отсутствующая колонка или другое представление, проверь `DESCRIBE TABLE chatium_ai.<имя>` в целевом аккаунте. Отказ доступа отличается от пустой выборки.
3. Выбери подходящий шаблон из [рецептов](references/queries.md): просмотры, сотрудники, UTM сессий, события или расходы. Сохрани определения метрик пользователя; добавляй фильтры веб/приложение, сотрудники/клиенты, боты и пути только по смыслу задачи.
4. Выполни один ограниченный запрос через SDK. Аналитику агрегируй в SQL; для подробных списков задай `LIMIT` и сортировку. Проверяй форму результата и ошибки до расчётов в JS. Ноль, отсутствие данных и неуспешный запрос — разные результаты.
5. Сообщи аккаунт, точный период/часовой пояс, единицы, фильтры и ограничения. Таблица в чате достаточна для небольшого результата; файлы и dashboards создавай по задаче. При топ-N среднее/медиану считай по всей заявленной популяции, а не по этим N строкам.

Для разовой выборки запускай код через авторизованный Chatium CLI из checkout целевого аккаунта по [контракту chatium exec](../chatium-development/exec.md):

```sh
chatium exec <<'EOF'
import { queryAi } from '@traffic/sdk'
return {
  account: { id: ctx.account.id, name: ctx.account.name },
  result: await queryAi(ctx, 'SELECT timezone() AS timezone, now() AS server_time'),
}
EOF
```

CLI исполняет серверный код из Source Build; сверяй сообщённый `Executed commit`, не считай незакоммиченные локальные изменения исполняемыми. Для постоянного отчёта вызывай SDK из серверного обработчика с проверкой прав на аналитику аккаунта. Браузер обращается к этому обработчику, не к SDK напрямую. Если нет авторизации, установленного Traffic или подходящей сборки, сообщи конкретный блокер; не создавай публичный диагностический роут ради чтения.

## Область доступа

`queryAi` вызывает функцию плагина, которая задаёт текущий account context и read-only настройки. Обращайся к `chatium_ai.access_log`, `chatium_ai.behaviour2_log`, `chatium_ai.traffic_source_statistics`. Эти представления уже фильтруют аккаунт и не экспортируют `account_id`: такой фильтр или GROUP BY здесь не нужен и не сработает.

Используй SELECT/WITH для данных и DESCRIBE/SHOW CREATE для схемы. Не подставляй чужой контекст, не меняй служебные настройки, не добавляй `SETTINGS`, не переходи к `counter_app.*`, учётным данным ClickHouse или `rawQuery` для обхода ограничений. Этот скилл предназначен для одного аккаунта; недоступность глобальных данных не устраняется другим SQL-фильтром.

Сервер разрешает account caller и определённые плагины, а не любой plugin caller. GetCourse-аккаунты вида `<цифры>-gc` текущая реализация отклоняет. `Invalid caller` и `Not implemented here!` — ограничения контракта, не повод маскировать вызывающего.

## Правила подсчёта

- `dt` ограничивает чтение по дням; `ts`/`ts64` задаёт точный полуоткрытый интервал `[from, to)`. Для серии запросов зафиксируй одну границу `to`. Часовой пояс узнай через `timezone()`, не наследуй его из компьютера агента.
- `uid` — идентификатор посетителя, `sid` — аналитическая сессия, `user_id` — пользователь. `session_id` не замена `sid`. `resolved_user_id` может разрешать анонимную историю и возвращать visitor ID; это не доказательство авторизации. Пустые идентификаторы исключай из уникальных подсчётов.
- `access_log` смешивает просмотры, служебные запросы и бизнес-события. Просмотры приложения — `screen_opened` или пустой `action` для старых сборок. `chat_opened` рядом с `screen_opened` — разные события, а не доказанный дубль. Для событий процесса фильтр просмотров и обязательный `sid` могут потерять нужные записи.
- Роль на момент события — `user_account_role`. `user_roles` устарело. Для сотрудников оставляй Staff/Admin/Developer/Owner и служебные пути; для клиентской аудитории при необходимости исключай эти роли. Логи показывают активность за период, а не текущий список выданных доступов.
- Смена роли создаёт пересечения между колонками. Если категории должны складываться в итог, задай приоритет классификации пользователя за период; рецепт объединяет Developer+Owner и относит остальных к Staff/Admin.
- В одном аккаунте разные домены обычно входят в одну выборку. Фильтруй домен только для явного разреза по сайту; root/platform аккаунт с чужими хостами требует отдельной интерпретации.
- Для воронок используй идентификатор сущности и порядок событий, а не только отношение независимых count. Период возникновения и окно конверсии задаются отдельно. Неизвестная семантика payload требует контракта события, а не догадки по имени колонки.
- Значения из внешнего ввода вставляй как SQL-литералы с корректным экранированием обратной косой черты и кавычки. Имена таблиц/колонок/сортировок выбирай из разрешённого набора. Примеры и подробности — в рецептах.

`filteredQueryAi` в проверенной версии не добавляет переданный date filter к SQL: это оболочка над `queryAi`. Условия периода пиши в самом запросе.
