# Домен и сайт

## Сначала прочитай привязки аккаунта

До вопросов о подключаемом домене получи список через SDK:

```ts
import { getDomains } from '@app/account/domain'
return { accountId: ctx.account.id, accountName: ctx.account.name, domains: await getDomains(ctx) }
```

Кратко покажи найденные имена и состояние привязок. Пустой список означает отсутствие
привязок в этом аккаунте, ошибка чтения — неизвестное состояние. Отсутствие имени
в списке ничего не говорит о том, куплен ли домен у регистратора.

Затем спроси: «Какой домен подключаем? Он уже у вас есть или вы только собираетесь
его купить?» Уже названное имя и известный ответ используй без повторного вопроса.
Приведи выбранное имя к нижнему регистру и IDNA/ASCII, без протокола, пути, порта
и конечной точки; сохрани отображаемое имя для ответа. Работай с указанным именем,
добавляя `www` или другие поддомены только по запросу.

### Домен ещё предстоит купить

Подскажи: «При покупке домена у регистратора укажите DNS-серверы Chatium:
`ns1.chatium.io` и `ns2.chatium.io`». Это настройка NS в панели регистратора;
почтовые и адресные записи будут настраиваться после покупки.

До подтверждения покупки дай эту инструкцию и сохрани выбранное имя; привязку
создавай после приобретения домена пользователем. Этот этап заканчивается ожиданием
покупки, а не отчётом о подключённом домене.

### Домен уже есть

Предложи два варианта, если способ ещё не выбран:

1. **На DNS-серверах Chatium:** прописать наши NS у регистратора. Chatium будет
   управлять DNS и сертификатом; действующие записи сайта, почты и других сервисов
   нужно перенести в нашу зону до смены NS. Режим SDK — `ZoneAndCert`.
2. **Оставить DNS у текущего провайдера:** напрямую прописать записи для сайта
   по адресам Chatium. NS остаются прежними, сертификат выпускает Chatium.
   Режим SDK — `OnlyCert`; конкретные значения покажи по инструкции ниже.

Сохрани уже выбранный пользователем способ или режим существующей привязки,
если его не требуется менять. Вариант с прокси/CDN и почтовый домен без переноса
сайта разбирай по таблице режимов; они не заменяют эти два обычных варианта.

## Прочитай состояние выбранного домена

Для существующей привязки вызови `getAccountDomainState(ctx, domain)`:
`domain` содержит `id`, `name`, `controlType`, `isReady`, `pathPrefix`, `dnsRecords`;
`isPrimary` относится к основному адресу аккаунта. `service` описывает CDM и может
быть `null`. `setup.nameservers`, `setup.addresses` и `setup.controlTypes` — реальные
значения для этого окружения. IP бери только из этого ответа. Перед сменой NS сверь
пару Chatium, указанную выше, с `setup.nameservers`; при расхождении выясни целевое
окружение и покажи различие пользователю.

Методы проверяют принадлежность домена аккаунту; установленному приложению нужны
`accountDomains: read/write` для соответствующих операций. Доступ к API не является
поручением менять другой аккаунт. Параметр `childAccount` в этом сценарии не нужен.

## Выбери режим и привяжи

| `controlType` | Когда использовать | Где меняются записи |
| --- | --- | --- |
| `ZoneAndCert` | Пользователь выбирает DNS Chatium и сертификат платформы | Делегирование у регистратора, зона через SDK Chatium |
| `OnlyCert` | DNS остаётся у текущего провайдера, сайт и сертификат обслуживает Chatium | Записи для сайта у текущего DNS-провайдера |
| `ProxiedCert` | Перед сайтом уже предусмотрен внешний прокси/CDN | DNS и прокси у выбранного провайдера; также проверяется маршрут к Chatium |
| `External` | Внешнее управление; например, привязка для почты при сохранении внешнего сайта | У внешнего провайдера; CDM не выдаёт сертификат и не управляет зоной |

Когда домен уже куплен, привязки ещё нет и режим выбран:

```ts
import { addAccountDomain, getAccountDomainState } from '@app/account/domain'
const domain = 'example.com' // заменить подтверждённым доменом
const added = await addAccountDomain(ctx, { name: domain, controlType: 'OnlyCert' })
return { added, state: await getAccountDomainState(ctx, domain) }
```

Это пример ветки с внешним DNS, а не общий выбор режима. Для изменения существующего
режима используй `updateAccountDomain(ctx, domain, controlType)`. Сначала проверь
сохранённое состояние; `addAccountDomain` не является универсальным upsert.
Если имя занято или не принадлежит аккаунту, останови эту операцию и сообщи причину.
Операторский `rebindDomainService` не используется для обхода владения.

## Покажи конкретные NS или DNS-записи

После добавления/смены режима перечитай `getAccountDomainState(ctx, domain)`.
В Dev (`/app/dev/domains`, вкладка подключения) значения показываются отдельно,
с возможностью скопировать каждое: `setup.nameservers` для DNS Chatium и
`setup.addresses` для прямого подключения. Дай пользователю такие же реальные
значения и место их ввода, а не предложение самостоятельно найти IP.

- **`ZoneAndCert`:** выведи каждый NS из `state.setup.nameservers` отдельной строкой
  для копирования. Указать их нужно в настройках DNS-серверов домена у регистратора;
  добавление NS-записей в старую зону само по себе не меняет делегирование.
- **`OnlyCert`:** Dev предлагает создать A-записи по каждому адресу из
  `state.setup.addresses`. Выведи таблицу **«Тип | Имя/хост | Значение»**, отдельную
  строку на каждый адрес. Для IPv4 тип — `A`, для IPv6 — `AAAA`. Для корня выбранной
  зоны имя обычно `@`, для `shop.example.com` в зоне `example.com` — `shop`;
  рядом укажи полное подключаемое имя. Учитывай формат панели провайдера, чтобы
  суффикс домена не добавился дважды. Сохрани текущий TTL либо используй значение
  по умолчанию провайдера: `setup` не задаёт TTL. NS, MX и почтовые TXT остаются
  прежними. Сверь старые A/AAAA/CNAME именно подключаемого имени и подготовь замену
  конфликтующих значений: оставленный старый адрес может направить часть запросов
  на прежний сервер.
- **`ProxiedCert`:** сохрани выбранный прокси и проверь его origin/TLS-настройки.
  Как в Dev, обычный список прямых A-записей здесь не является инструкцией для
  замены маршрута через прокси.

Если `setup` не вернул нужных значений, сообщи о пробеле и восстанови получение
инструкций. Примеры IP и адреса другого аккаунта не подставляются.
После внесения записей переходи к проверке состояния и обычного HTTPS-адреса.

## Дождись состояния платформы

После настройки повторно читай `getAccountDomainState`:

| Состояние | Следующее действие |
| --- | --- |
| `New` | Регистрация поставлена в очередь; повторить чтение |
| `WaitDelegate` | Сверить фактические DNS/маршрут с `setup` и `service.comment` |
| `Delegated` | Маршрут/делегирование принято, сертификат ещё готовится |
| `Ready` | Перейти к независимой проверке HTTPS |
| `Disabled` | Разобрать причину отключения; подключение не готово |
| `service: null` | Для `External` ожидаемо; в управляемом режиме регистрация не подтверждена |

`service.syncInProgress` означает незавершённую синхронизацию. Если нужно повторно
зарегистрировать уже сохранённую конфигурацию после исправления причины ошибки,
вызови `syncAccountDomain(ctx, domain)` один раз и продолжай чтение статуса.
Возврат `void` от sync не означает готовность.

У `External` флаг `domain.isReady` может быть установлен при привязке: это не
проверка DNS, сертификата или страницы. Для сайта заверши
[проверкой HTTPS](verification.md#сайт); почтовому домену без сайта она не требуется.

## Основной адрес и страница

Сделай домен основным только если это входит в запрос и сайт уже проверен:
`setAccountPrimaryDomain(ctx, { domain: domainId })`, где `domainId` взят из SDK.
Затем перечитай `isPrimary` и повтори открытие сайта с новым адресом/редиректами.
Сохрани прежний рабочий адрес для диагностики; не меняй Git remote ради основного домена.

Основной домен и стартовая страница — разные настройки. Если требуется назначить
конкретную страницу, прочитай [маршрутизацию доменных homepages](../../chatium-development/routing.md).
Проверь опубликованную страницу, а не только файл `.chatiumrc` в рабочей копии.

## Переход администратора на подключённый домен

После [проверки сайта](verification.md#сайт) покажи пользователю ссылку и предложи
продолжить работу на подключённом домене с сохранением авторизации. До этого нужны
свежая привязка к **тому же аккаунту**, готовность домена, публичный DNS и успешный
HTTPS с ожидаемой страницей аккаунта и проверенными редиректами. Одного `isReady`,
HTTP 200 или готовой почты недостаточно. При ожидающем сертификате, чужой странице
или непроверенном HTTPS сначала закончи диагностику. Если подключали только почту
и сайт остаётся внешним, переход в Code на этом домене не предлагай.

Используй служебную страницу Dev **на уже работающем адресе аккаунта, где пользователь
авторизован**. При работе с системного домена ссылка остаётся на нём. Возьми исходный
адрес из фактического URL текущей панели; учти её префикс пути, если он есть.
Формат для аккаунта без префикса:

```text
https://<текущий-домен>/app/dev/open?domain=<подключённый-домен>&path=%2Fapp%2Fdev%2Fcode
```

В `domain` передай точное проверенное имя из SDK, без `https://` и пути. В `path` —
локальный путь назначения: для продолжения работы в Chatium Code `/app/dev/code`,
для явно запрошенной другой страницы — её путь. Значения обоих параметров кодируй
через `encodeURIComponent` или `URLSearchParams`; query и `#fragment` назначения
должны целиком оставаться внутри `path`. Префикс **целевого** домена страница добавит
по привязке сама — повторно включать его в `path` не нужно.

В итоговом ответе дай готовую Markdown-ссылку с подписью **«Перейти на домен example.com»**,
подставив реальный домен и адрес ссылки. Например: «Домен example.com подключён,
проверки DNS и HTTPS прошли. [Перейти на домен example.com](https://account.chatium.ru/app/dev/open?domain=example.com&path=%2Fapp%2Fdev%2Fcode).
На открывшейся странице нажмите кнопку перехода, чтобы продолжить в Chatium Code».
Служебный путь отдельным текстом пользователю не показывай: страницы нет в меню,
на ней только кнопка «Перейти на домен {домен}».

В чат отдавай именно эту ссылку **без токена авторизации**. Страница повторно проверяет
домен и создаёт короткоживущую ссылку через `authenticateCurrentUserInNewDomainOrBrowser`
только после нажатия кнопки пользователем. Выписывать токен заранее через `chatium exec`,
публиковать URL миграции с токеном или нажимать кнопку вместо пользователя не нужно.
Переход не требует смены основного домена аккаунта.

Текущая служебная страница требует реального пользователя с ролью Developer или Owner,
режим авторизации аккаунта `Multi` и действующую браузерную сессию. Если известно,
что эти условия не выполнены или Dev недоступен, назови конкретное ограничение
и не обещай перенос авторизации. При истёкшей сессии предложи войти на исходном
рабочем адресе и снова открыть служебную ссылку; роль ради перехода не повышай.
