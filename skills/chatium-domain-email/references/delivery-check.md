# Автоматическая проверка доставки

Используй после поручения проверить отправку или подключить почту с проверкой
доставки. Одно контрольное письмо отправляется в общий ящик
`diagnostics@email.chatium.ru`. Отправитель — выбранный активный общий ящик
пользователя. Друзьям, сотрудникам и клиентам этот тест ничего не отправляет.
Если поручение ограничено чтением настроек без отправки, сохрани это ограничение.

## Запусти одну проверку

Проверь отправителя по [сценарию подключения](verification.md), прочитай актуальные
типы `@email/sdk`. Локально сгенерируй UUID, сохрани его вместе с аккаунтом,
транспортом и ящиком **до вызова**. Подставь сохранённый UUID и реальные значения:

```ts
import { startEmailDeliveryCheck } from '@email/sdk'

return await startEmailDeliveryCheck(ctx, {
  transportId: 'TRANSPORT_ID',
  mailbox: 'support@example.com',
  idempotencyKey: 'SAVED_UUID_FOR_THIS_CHECK',
})
```

SDK сам задаёт диагностического получателя, текст и уникальный маркер. Сохрани
`check.id` и `check.deadlineAt`. `success:true` означает, что результат проверки
создан; готовность доставки определяй по `check`, а не по этому флагу.

После обрыва вызова повтори `startEmailDeliveryCheck` с теми же аргументами и UUID:
он вернёт прежнюю проверку без нового письма. `idempotency_conflict` означает,
что этот ключ уже использован для другого ящика/транспорта. При неизвестном исходе
сохрани проверку и читай её результат; новый ключ для повторной отправки не создавай.

`diagnostics_not_configured` требует настройки общего приёмника оператором Email.
Настройка webhook и MX общего ящика не входит в работу с аккаунтом клиента.
`diagnostic_rate_limit` ограничивает новые проверки десятью в час на аккаунт;
существующую проверку продолжай читать. При отсутствии SDK обнови типы и проверь
серверный вызов; доступность метода определяй по нему.

## Получи подтверждение

Из того же аккаунта вызывай `getEmailDeliveryCheck` примерно раз в 30 секунд
до результата или `deadlineAt` (окно ожидания — 10 минут). Это чтения, не отправки.
В примере подставь сохранённый ID и ожидаемого отправителя:

```ts
import { getEmailDeliveryCheck } from '@email/sdk'

const checkId = 'SAVED_CHECK_ID'
const result = await getEmailDeliveryCheck(ctx, { checkId })
if (!result.success) return { phase: 'delivery-check', result }
const check = result.check
return {
  checkedAt: new Date().toISOString(),
  accountId: ctx.account.id,
  check,
  diagnosticDeliveryVerified:
    check.id === checkId && check.transportId === 'TRANSPORT_ID' &&
    check.from === 'support@example.com' && check.to === 'diagnostics@email.chatium.ru' &&
    check.status === 'received' && check.deliveryVerified === true &&
    typeof check.receivedAt === 'string' && Number.isFinite(Date.parse(check.receivedAt)),
}
```

Результаты:

- `received` — подписанное входящее событие и прочитанное письмо подтвердили
  совпадение получателя, отправителя и маркера. Сообщи время получения и ID проверки.
- `waiting` — письмо пока не найдено; продолжай ограниченный опрос.
- `not_received` — получение за время ожидания не подтверждено. Это не доказательство
  потери письма; сообщи последний статус и сохрани ID для позднего чтения.
- `send_failed` / `delivery_failed` — отправка отклонена или зафиксирована ошибка
  доставки; разбери `sendError` и `submission.recipients`.
- `submission_unknown` — сервис не подтвердил приём отправки. Дождись входящего
  подтверждения в пределах того же окна; повторное письмо автоматически не отправляй.

`submission` содержит отдельный SMTP-статус. Даже `delivered` без входящего
подтверждения оставляет `diagnosticDeliveryVerified:false`.
`submissionCheckError` означает, что последнее чтение SMTP-статуса не удалось;
не выдавай сохранённый снимок за свежий. Ошибка чтения самой проверки оставляет
результат неизвестным. После истечения окна закончи опрос и сообщи наблюдения.

## Границы результата

Этот тест проверяет отправку из выбранного ящика и получение на общем приёмнике.
Приём писем **в ящик клиента** проверяется отдельным согласованным входящим письмом.
Попадание во «Входящие» Gmail, Яндекса и Mail.ru оценивается по доступному ящику получателя
или обратной связи получателей из [прогрева](warmup.md).

SPF/DKIM/DMARC агент проверяет сам по доступным данным сервиса. Клиента не проси
самостоятельно разбирать DNS или заголовки. Текущий отчёт возвращает
`authentication:'not_checked'` и `inboxPlacement:'not_checked'`: результаты
аутентификации входящего письма и папка внешнего получателя через этот API ещё
не доступны. Назови этот пробел; получение контрольного письма не превращает его
в `pass` и не подтверждает готовность к массовой рассылке.
