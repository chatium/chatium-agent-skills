# Адресаты прогрева: пользователи и CRM

Используй при [подборе аудитории прогрева](warmup.md). Выполняй запросы в целевом
аккаунте через `chatium exec`; читай актуальные declarations установленных SDK.
Сначала получи данные и подготовь группу, затем переходи к согласованной отправке.

## Друзья и сотрудники

Пользователи аккаунта — источник кандидатов. Старый `@app/users` не предоставляет
список сотрудников; актуальный метод — **`findUsers` из `@app/auth`**.
Используй реальные аккаунты с ролями `Staff`, `Admin`, `Developer`, `Owner`.
`confirmedEmail` — подтверждённый адрес пользователя; поле `email` не является
контрактом современного `SmartUser`. Подтверждение адреса не означает согласие
на проверку. Служебных пользователей, включая `support`, в группу не включай.

```ts
import { findUsers } from '@app/auth'

const offset = 0 // Для следующей страницы используй nextOffset предыдущей.
const limit = 100
const users = await findUsers(ctx, {
  where: { type: 'Real', accountRole: ['Staff', 'Admin', 'Developer', 'Owner'] },
  offset,
  limit,
})
const warmupStaffPage = {
  candidates: users.filter(user => user.username !== 'support').map(user => ({
    userId: user.id,
    name: user.displayName,
    email: user.confirmedEmail || null,
  })),
  nextOffset: users.length === limit ? offset + users.length : null,
}
return warmupStaffPage
```

При необходимости продолжи страницы, пока не найдены кандидаты или не исчерпан
список. Пустая группа после фильтрации не означает конец списка: смотри `nextOffset`.
Предложи найденных людей, запроси только отсутствующие адреса; адреса друзей можно
просто получить в чате. Создавать им учётные записи или просить пользователя
заполнять карточки ради отправки не нужно. Если кандидатов нет, пропусти вариант.

## Прошлые клиенты

Проверь наличие заказов через **`findDeals` из `@crm/sdk`**. Если CRM недоступна,
различай отсутствие приложения/доступа и пустую базу. Не устанавливай CRM и не
предлагай заносить заказы вручную только ради прогрева.

```ts
import { findDeals } from '@crm/sdk'

const offset = 0
const page = await findDeals(ctx, { offset, limit: 100, order: 'desc' })
const nextOffset = page.offset + page.deals.length
if (page.deals.length === 0 && nextOffset < page.total) {
  throw new Error('CRM вернула неполную страницу; отсутствие заказов не подтверждено')
}
const warmupOrderPage = {
  deals: page.deals,
  total: page.total,
  nextOffset: nextOffset < page.total ? nextOffset : null,
}
return warmupOrderPage
```

Каждый элемент `page.deals` — **`DealView`**: `deal`, `contacts`, `customers`,
`customerResolution`. Email находится в контакте с `type: 'email'`, его
`valueNormalized`/`valueRaw`; связь с клиентом — `customerId`. Не ищи email в
несуществующем поле сделки. `deal` содержит `status`, `dealCreatedAt`, `dealClosedAt`,
`paymentStatus`, `pipelineId`, `stageId`, `sourceSystem`, `subject` и `customFields`.
При необходимости запроси детали через `getDeal(ctx, { id })`.

1. Определи, какие сделки представляют заказы и какие статусы/этапы означают
   выполненный заказ в этом аккаунте. `won` и дата закрытия — признаки для проверки,
   но оплата или закрытая продажа могут предшествовать выполнению заказа. Выбирай
   подтверждённые прошлые покупки, предпочтительно недавние; отмена, проигранная
   сделка и тестовая оплата сами по себе прошлой покупкой не считаются.
2. Для каждого кандидата проверь **все его заказы**, включая другие воронки:
   `findDeals(ctx, { customerId, offset, limit: 100 })`, без фильтра `status: 'won'`.
   Пройди страницы по `total` и фактическому размеру ответа. Клиента с актуальным
   заказом исключи, даже если у него есть завершённые. Неполный запрос, ошибка,
   неизвестный статус или неоднозначный `customerResolution` оставляют кандидата
   непроверенным; включать его до прояснения нельзя.
3. Свяжи email с нужным клиентом, проверь дубли и другие карточки с тем же адресом.
   Для поиска доступны `contactsFindAll(ctx, { where: { type: 'email',
   valueNormalized: email }, limit: 100, offset })` и проверка заказов найденных
   `customerId`. Общий email с активным заказом в другой карточке тоже исключи.
   Используй нормализацию CRM; самостоятельно склеивать Gmail-адреса по точкам
   или удалять `+suffix` не нужно. Один человек получает одно письмо, один адрес
   используется один раз.
4. Убедись, что письмо ожидаемо и уместно, учти согласие на рассылку, отписки,
   блокировки и известные недоставляемые адреса. Сам факт покупки не означает
   подписку на любые рекламные письма. Используй доступные сведения CRM/Sender;
   если основание неизвестно, подготовь группу и уточни его у пользователя.
5. Собери до 100 подходящих уникальных контактов, ориентируясь на группу 10–100.
   Сохрани для каждого email, ID клиента и прошлого заказа, дату/основание отбора
   и результат проверки актуальных заказов. Набрать заданное число любой ценой
   не нужно. Перед отправкой обнови проверку актуальных заказов и ограничений.

Не выгружай всю базу в ответ пользователю. Покажи размер группы, критерии, причины
исключений и подготовленную первую партию. Достаточность обхода оценивай по проверке
истории выбранных людей; первая страница всей CRM не доказывает отсутствие других
заказов у них. Ошибка чтения не превращается в «заказов нет».

## Отправка клиентской группе

Подготовь текст и точный список первой партии по [сценарию прогрева](warmup.md).
Выполни отправку сам через штатный путь рассылки, который сохраняет отписки и
ограничения получателей. Для сохранённого письма используй [Mailings SDK](../../chatium-development/mailings.md);
для подготовленного текста — [Sender SDK](../../chatium-development/sender-messaging.md#sendmessagetocontacts):

- Выбери существующий email-канал **настраиваемого домена** по
  [SDK каналов](../../chatium-development/sender-entities.md#подключение-и-выбор-канала).
  У `sendMessageToContacts` задай непустой `channels: [emailChannelId]`,
  `contacts: [{ type: 'email', value: email }]`, `expandCustomerContacts: false`,
  `isMailing: true`, `originType: 'mailing'`, сохранённый `originId` партии.
- В `message` передай `subject`, `plain`/`html`; нужного отправителя задай
  через `extra: { senderName, emailUsername }`, где `emailUsername` — локальная
  часть адреса на домене выбранного канала. Проверь фактический From и работающую
  отписку. Клиентскую рассылку не маскируй под транзакционное письмо.
- Перед каждым вызовом сохрани адрес и состояние операции в журнале партии.
  `originId` связывает аналитику, но не обещает идемпотентность. При сетевой ошибке
  сначала выясни результат существующей отправки; неизвестный исход не повод
  заново вызвать отправку всей партии или того же письма.
- Проверь `results` по каждому адресату/каналу, сохрани ID сообщений, отказы,
  пропуски и доступные статусы доставки. `success` верхнего уровня не доказывает
  доставку всем, а очередь и SMTP-приём не доказывают попадание во «Входящие».
  Отписанных/заблокированных не включай повторно через другой API или канал.

SDK сам создаёт необходимые объекты переписки. Пользователю достаточно согласовать
подготовленную отправку, если разрешения ещё нет; ручная загрузка базы и работа
в редакторе рассылок не нужны. Дальнейший объём выбирай по наблюдаемым результатам,
а не по числу оставшихся адресов.
