# Изменения DNS

Источник целевых NS/IP — `getAccountDomainState().setup`; почтовых записей — свежие
`checkEmailTransportDns().checks`. Сохраняй `name`, `type`, `value`, `purpose` и `ok`.
Значения зависят от домена и сервиса: MX, DKIM-селекторы, ownership-токены и SPF не
подставляются из образца. Публичный DNS-токен владения не является ключом доступа к CES.

## Выбери место изменения

- `ZoneAndCert`: проверь состояние делегирования, затем читай
  `getDomainDnsRecords(ctx, domain)`. Он возвращает `draft`, `revision`,
  `syncInProgress` и отдельные `servers[].records`.
- `OnlyCert`, `ProxiedCert`, `External`: меняй записи у внешнего DNS-провайдера.
  SDK Chatium не редактирует его зону. Если доступа нет, подготовь таблицу записей
  для пользователя и продолжи проверку после их внесения.
- Системный домен аккаунта: следуй [ветке Email](email.md#системный-домен).
  Не переводи его в `ZoneAndCert` и не редактируй родительскую зону платформы.

Запись с `readOnly: true` принадлежит платформе. `managedByApi: true` защищает её
от перезаписи формой полной зоны, но не делает разрешённым изменение чужого сервиса.
Меняй только RRset, входящие в согласованную задачу.

## Почтовые записи в зоне Chatium

Для точечных изменений используй `patchDomainDnsRecords`, не полную пересборку зоны:

```ts
import { getDomainDnsRecords } from '@app/account/domain'
return await getDomainDnsRecords(ctx, 'example.com')
```

Из этого снимка и почтовых checks собери `changes: DomainDnsChange[]`, импортируя тип
из `@app/account/domain`. Пока `syncInProgress` истинно, дождись завершения текущей
публикации. Примени подготовленный массив через `patchDomainDnsRecords(ctx, domain,
changes)` по этим правилам:

1. Каждый элемент заменяет **весь RRset** одного имени/типа. Имя абсолютное с конечной
   точкой; разрешены `A`, `AAAA`, `CNAME`, `MX`, `SRV`, `PTR`, `TXT`, `NS`.
   `records`/`expected` — массивы `{ content, disabled }`; TTL берётся из текущей
   записи либо согласованного нового значения. Один вызов принимает до 30 элементов.
2. Сверь соответствующий RRset на **каждом** authoritative-сервере. Нужен полный
   сохранённый набор, включая disabled-записи. `expected` содержит прочитанные значения,
   `records` — полный целевой набор. `expected: []` допустим только для проверенно
   отсутствующего набора; `records: []` удаляет его.
3. `TXT.content` — DNS presentation format: строки в кавычках, при необходимости
   несколько сегментов. Это отличается от обычного `checks[].value`. Разбирай и
   сохраняй существующие сегменты и escape-последовательности; одной внешней парой
   кавычек нельзя безопасно преобразовать любое значение. MX включает приоритет
   и имя сервера в формате, который возвращает SDK/принимает провайдер.
4. Если серверы расходятся, не выбирай первый как истинный. После частично выполненного
   **этого же** запроса допустим повтор с прежними `expected` и целевыми значениями:
   уже совпадающее целевое значение считается успешным. Неизвестное расхождение требует
   повторного чтения/разбора; `DNS_CONFLICT` не обходится заменой `expected` вслепую.
5. После вызова повторно прочитай все снимки. Принятие патча всеми authoritative-серверами
   не доказывает обновление DNS-кешей или готовность почты; повтори проверки потребляющего SDK.

## Сохрани действующие сервисы

Для почты цель определяется назначением записи:

- **MX / inbound:** замена меняет, куда приходит почта всего этого имени. Если там
  работает другой провайдер, подготовь конкретный план переноса и дождись решения
  пользователя. Не добавляй второй независимый почтовый сервис как способ «оставить оба».
  Подключение только исходящей почты не даёт оснований переносить входящую. Если
  текущий API требует inbound MX для `ready`, объясни ограничение и оставь эту часть незавершённой.
- **SPF / bounce-spf:** сохрани уже разрешённых отправителей и действующую политику.
  Добавляй требуемые механизмы в единственную SPF-политику, до завершающего `all`.
  Несколько SPF-записей, сложный `redirect` или неясное объединение требуют разбора,
  а не второй TXT-политики или замены всех TXT на возвращённый пример.
- **DMARC:** сохрани существующие `p`, отчётные адреса и остальные параметры. Не ослабляй
  политику до `p=none` ради совпадения с шаблоном проверки.
- **DKIM и ownership:** используй только имя/значение из текущих checks, сохраняя чужие
  селекторы, проверочные TXT и прочие записи на том же имени. Конфликт существующего
  ключа/ownership-записи сначала разбери, а не перезаписывай как пустое место.

Для внешнего DNS укажи, ожидает ли его форма относительное имя или FQDN: проверь
итоговую запись, чтобы домен не был дописан дважды. При смене NS подготовь все
нужные записи до делегирования и учитывай действующие настройки регистратора,
включая DNSSEC, если он включён; неполный снимок зоны не является планом переноса.

## Если пользователь меняет DNS-черновик

Этот путь нужен для работы с редактором всей зоны. `saveDomainDnsRecords(ctx, domain,
records, revision)` сохраняет **полный** редактируемый массив, не публикуя его.
Сохраняй остальные записи и уникальные `id`. В этом формате имена относительные
(`@` — вершина), запись имеет `{ id, type, name, value, ttl }`.

Передай **возвращённую сохранением** `revision` в `applyDomainDnsRecords(ctx, domain,
revision)` только когда задача включает публикацию всего черновика. Apply ставит
публикацию в очередь; отслеживай `syncInProgress` и реальные снимки серверов.
При `DNS_DRAFT_CONFLICT` перечитай черновик, сохрани чужие изменения и пересобери
предлагаемую правку. API-managed записи редактируются точечным патчем.
