# Формат: каталог, поля, настройки

## Схема

```
.knowledge-base/
  .knowledge.yml                 # порядок баз и оформление портала
  product/
    .knowledge.yml               # настройки базы
    introduction.md              # статья
    getting-started/
      .knowledge.yml             # настройки раздела
      installation.md            # статья
```

- Имя папки — адрес базы и раздела, имя файла статьи — адрес статьи.
- Свой `.knowledge.yml` есть у портала (корень `.knowledge-base/`), у базы и у каждого раздела.
- Slug в YAML не дублируется: он и есть имя файла или папки, а отображаемое название живёт в `title`. Поэтому смена названия адрес не меняет.
- Все поля необязательные. Отсутствие поля — норма, а не поломка; значения по умолчанию ниже.

## Корневой конфиг: `.knowledge-base/.knowledge.yml`

Два поля: `order` — порядок папок баз, `portal` — единое оформление всех баз портала.

```yaml
order:
  - product
  - support

portal:
  publicFont: golos
  publicAccentColor: "#dc1d51"
  publicSeoImageFileHash: null
  publicSeoImageFileName: null
  publicSeoImageFileType: null
```

| Поле `portal` | Значения | По умолчанию |
| --- | --- | --- |
| `publicFont` | `golos`, `inter`, `manrope`, `pt-sans`, `pt-serif`, `system` | `golos` |
| `publicAccentColor` | HEX-строка `"#RGB"` или `"#RRGGBB"` | `"#dc1d51"` |
| `publicSeoImageFileHash` | Vault-хэш изображения либо `null` | без резервной обложки |
| `publicSeoImageFileName` | имя файла либо `null` | не задано |
| `publicSeoImageFileType` | MIME-тип — `image/png`, `image/jpeg`, `image/webp` и подобные; закрытого списка нет | не задано |

Неизвестное название шрифта и некорректная строка цвета молча заменяются значениями по умолчанию: оформление не сломается, но и не станет тем, что написано. Оформление портала меняется только по прямой просьбе.

## Конфиг базы и раздела

```yaml
title: Продукт
description: Документация продукта
order:
  - introduction.md
  - getting-started

publicAccessMode: disabled
agentAccessMode: enabled
archivedAt: null
archivedBy: null
isNew: false
```

| Поле | Значения | Если отсутствует |
| --- | --- | --- |
| `title` | строка | название выводится из имени папки; при публикации статьи название обязательно |
| `description` | строка — описание базы | без описания |
| `order` | массив непустых строк — имён непосредственных детей, либо `[]` | сортировка по названию |
| `publicAccessMode`, `agentAccessMode` | `inherit`, `enabled`, `disabled` | `inherit` |
| `archivedAt` | ISO-дата со временем, например `"2026-09-21T10:00:00.000Z"`, либо `null` | не архивировано |
| `archivedBy` | непустая строка — ID пользователя, либо `null` | автор архивации неизвестен |
| `isNew` | `true` или `false` — именно boolean, без кавычек | `false` |

- У раздела конфиг тот же, но без `description`: это поле базы.

## Frontmatter статьи

```markdown
---
title: Установка
icon: "🚀"
cover: vault_file_hash
publicAccessMode: inherit
agentAccessMode: inherit
archivedAt: null
archivedBy: null
isNew: true
---

# Установка

...
```

| Поле | Значения | Если отсутствует |
| --- | --- | --- |
| `title` | строка; для публикации нужна непустая | черновик зовётся по имени файла, при публикации название спросят |
| `icon` | строка, обычно эмодзи; фиксированного списка нет | без иконки |
| `cover` | Vault-хэш изображения — не URL и не путь к файлу | без обложки |
| `publicAccessMode`, `agentAccessMode` | `inherit`, `enabled`, `disabled` | `inherit` |
| `archivedAt`, `archivedBy`, `isNew` | как в конфиге базы и раздела | не архивировано, `false` |

`null` для `title`, `icon` и `cover` означает то же, что отсутствие поля.

## Доступ, архив, метка NEW

Доступ идёт по двум независимым осям: `publicAccessMode` — читателю со стороны, `agentAccessMode` — ИИ-агентам аккаунта. Одной осью другую не заменить.

| Значение | Что значит |
| --- | --- |
| `inherit` | наследовать от родителя; у базы родителя нет, поэтому для неё это «доступ выключен» |
| `enabled` | разрешить |
| `disabled` | запретить |

- Без настроек база закрыта, разделы и статьи наследуют её состояние.
- **Ось агентов — жёсткое управление.** `agentAccessMode` решает, разрешён материал ИИ-агентам аккаунта или нет; агент ищет по базе и читает отдельные статьи, но только разрешённые. В файлах базы решается ровно это: пускать агента или не пускать.
- `enabled` **не обходит** явно закрытый или заархивированный родительский раздел. Открыть дочернюю статью под закрытым разделом нельзя — сначала открывают раздел.
- `disabled` у базы — закрытое состояние по умолчанию, но отдельную статью можно открыть явно.

**Архив.** Архивировано то, у чего заполнен `archivedAt`; `archivedBy` — только подпись, по нему архив не определяется. Для восстановления очищаются оба поля. Архив папки скрывает всю ветку.

**Метка NEW.** `isNew` — boolean без кавычек. Метка показывается у статей и разделов; отдельной метки NEW у базы нет.

**Что делает агент.** Доступы, архив и метку NEW агент меняет только по прямой просьбе и никогда по своей инициативе.

- `archivedBy` заполняется ID того, кто попросил, если он известен. Неизвестен — не выдумывай: спроси или оставь `null`.
- Метку NEW можно предложить поставить или снять, но не ставить автоматически при создании статьи.
- Архив и переименование — не одно и то же, и ни то, ни другое не делается молча.

## Кавычки в значениях

YAML ломается на двоеточии с пробелом внутри значения, режет значение на `#` и путается на кавычках. В названиях и цветах это встречается постоянно:

```yaml
title: H6. Поводы хода: данные, время, сообщение    # ошибка
title: "H6. Поводы хода: данные, время, сообщение" # верно
publicAccentColor: #dc1d51                          # ошибка: # начинает комментарий
publicAccentColor: "#dc1d51"                        # верно
```

Правило: **значение с двоеточием, решёткой или кавычкой бери в двойные кавычки.** Внутри кавычек `"` экранируется как `\"`.

Касается не только статей, но и `.knowledge.yml`: `title`, `description`, элементы `order` и значения `portal` подчиняются тем же правилам.

Платформа ответит `Nested mappings are not allowed in compact mappings` и откажется публиковать базу; при этом уже опубликованная версия не меняется — читатель продолжает видеть прежний текст. После исправления публикацию запускают заново: кнопкой в интерфейсе или новым пушем в `main`.

Перед сохранением полезно прогнать по базе:

```sh
grep -rn ': .*: ' .knowledge-base
```

Это черновая проверка: она покажет и строки тела статьи, где двоеточие безвредно (обычный Markdown), — смотри только на frontmatter и на `.knowledge.yml`. Двоеточие в заголовке `# ...` внутри статьи ничего не ломает.

## Настройки и публикация

- **Правка доезжает до читателя, когда попадает в `main`.** `git push origin HEAD:main` — это и есть публикация: ветка `main` и есть опубликованное состояние базы.
- **Содержимое статьи читатель видит из опубликованного снимка**, поэтому текст без публикации не меняется.
- **Доступ, архив и метка NEW читаются из самих файлов** и отдельной публикации не требуют: снимок для них не нужен.
- Правки, сделанные в интерфейсе базы, живут в отдельной ветке, а кнопка публикации в интерфейсе мержит её в `main`.
- Отсюда разные обещания в ответе: «доступ уже изменился» и «текст появится после публикации» — не одно и то же.
- Публикацию запускает не агент по своему усмотрению: пуш в `main` согласуется с пользователем (см. «Цикл работы» в `SKILL.md`).

## Незнакомые поля и комментарии

Неизвестные валидные YAML-поля и комментарии сохраняются при изменении настроек — платформа их не вычищает и тебе не надо. Правишь то поле, о котором просили, остальное оставляешь как было.

Своих полей при этом не изобретаем: поле, которого платформа не знает, она сохранит, но использовать не станет — и настройка молча не сработает (см. «Границы» в `SKILL.md`).

## Порядок и `order`

`order` перечисляет **непосредственных детей**: файл — с расширением (`.md`), папку — без расширения. Статьи и разделы можно перемешивать. В корневом файле `order` перечисляет папки баз.

Как строится дерево:

1. Сначала элементы, перечисленные в `order`, — в указанной последовательности.
2. Затем всё остальное — **по отображаемому названию**.

Отсюда два следствия, которые важно не перепутать:

- **Неуказанный элемент не пропадает.** Файл или раздел, которого нет в `order`, просто окажется после перечисленных, в алфавитном порядке названий.
- **`order` — про редакционный порядок, а не про видимость.** Меняй его, когда нужна осмысленная последовательность чтения (например, «Начало работы» перед «Справочником»). Добавлять туда каждый новый файл необязательно.

Ссылка на отсутствующий элемент игнорируется — дерево из-за неё не ломается.

## Как заводить

Имена папок и файлов — короткие латинские слаги (`context`, `legacy-ai-agents.md`): это адреса, а не то, что видит читатель. Человеческое название живёт в `title` — так папка `context` подписана «Рамки».

**Корневой конфиг.** `.knowledge-base/.knowledge.yml` — единственное место, где живут порядок баз и оформление портала. Нет файла — создай его, когда заводишь первую базу.

**Базу.** Создай `.knowledge-base/<slug>/.knowledge.yml` с `title` и, если нужно, `description` и `order`. Впиши имя папки базы в `order` корневого файла, если важен порядок баз.

**Раздел.** Создай папку с осмысленным именем и `.knowledge.yml` с `title` и `order`. Впиши имя папки в `order` родителя, если раздел должен стоять на определённом месте, а не в конце дерева.

**Статью.** Создай `<имя>.md` с frontmatter (`title` обязателен, `icon` и `cover` — по желанию). Впиши имя файла в `order` своего раздела, если важен порядок чтения.

**Правку статьи.** Меняется тело файла и, при необходимости, `title` во frontmatter.

**Настройку доступа, архива, метки NEW** — в конфиге базы или раздела либо во frontmatter статьи, и только по прямой просьбе.

**Оформление портала** — только по прямой просьбе: шрифт из списка, цвет HEX-строкой в кавычках.

**Переименование файла** — это смена адреса: поправь `order` родителя и ссылки на статью в других статьях. Иначе она съедет в конец дерева, а ссылки перестанут вести куда надо.

**Обложку.** `cover` — хэш файла в хранилище аккаунта, а не ссылка (см. «Вложения и обложки»).

## Вложения и обложки

Файл живёт в хранилище аккаунта, а в статью попадает только его хэш. Подставь фактический путь к предоставленному пользователем файлу; `./screenshot.png` ниже — пример относительного пути.

```sh
chatium storage upload --protected ./screenshot.png
```

Команда печатает блок на каждый файл. Здесь `<file_hash>` обозначает фактический хэш с расширением из ответа, а не готовое значение для копирования:

```
file: ./screenshot.png
file_hash: <file_hash>
download_url: https://fs.chatium.ru/download/<file_hash>
get_url: https://fs.chatium.ru/get/<file_hash>
thumbnail_url: https://fs.chatium.ru/thumbnail/<file_hash>/s/800x
```

- В `cover` и в `:::knowledge-attachment` идёт **`file_hash` как напечатан** — вместе с расширением. URL-ы из ответа в статью не вставляй: адресом вложения служит сам хэш.
- Вложения всегда грузятся с флагом `--protected`: файл не открывается по одной прямой ссылке, как обычный. Загруженный без флага внутренний материал оказывается доступен наружу.
- Файл, приложенный пользователем в чат: адрес вида `https://fs.chatium.ru/get/<hash>` уже содержит хэш — бери его оттуда, второй раз загружать не нужно. Если доступен только локальный файл, возьми его фактический путь из текущего окружения или сообщения пользователя и загрузи командой выше.
- `cover` — только обложка статьи, вложение в текст — только строкой `:::knowledge-attachment`. Одно другое не заменяет.
- Ни временных ссылок, ни локальных путей — ни в `cover`, ни в теле статьи.

## Ссылки между статьями

Ссылка — обычный Markdown, но ведёт на адрес reader, а не на файловый путь:

```markdown
[Установка](/app/knowledge/~/product/start/install.md)
```

Это ссылка на файл `.knowledge-base/product/start/install.md`: путь внутри базы, расширение `.md` сохраняется, домен можно не указывать.

- Относительные ссылки (`./install.md`, `../install.md`) и путь `.knowledge-base/...` **не поддерживаются** — renderer такой адрес отбрасывает.
- Постоянные ID статей живут в Heap и тоже работают в ссылках, но при работе с файлами формируй path URL.
- Маркеры `[[knowledge-article:ID]]` больше не нужны.

## Спецблоки в теле статьи

**Вложение из хранилища** — отдельной строкой, закрывающий `:::` не нужен:

```
:::knowledge-attachment FILE_HASH
```

Указывается Vault-хэш файла, а не внутренний ID вложения. Отображение зависит от типа файла: изображение — inline, видео и аудио — плеер, Markdown — боковой просмотр, остальные файлы — скачивание. Новый `knowledge-source` не создаём.

**Аккордеон:**

```html
<accordion title="Подробнее">

Обычный Markdown внутри.

- Первый пункт
- Второй пункт

</accordion>
```

Открывающий тег должен помещаться в одну физическую строку.

**Видео Muuvee:** `[muuvee:VIDEO_ID]` — здесь ID видео Muuvee, а не хэш хранилища.

**Цитата, врезка** — обычный Markdown: `> Важное замечание.`

Произвольный HTML и другие виды callout-блоков считать поддерживаемыми не нужно.

## Грабли

- **Переименовали файл, а `order` и ссылки — нет.** Статья не исчезнет, но съедет в конец дерева, а ссылки на неё сломаются.
- **`order` ссылается на то, чего нет.** Дерево не ломается — ссылка игнорируется, — но это след переименования: убери запись или восстанови файл.
- **Файл лежит не на своём уровне.** Статья не появится в разделе, если лежит выше или ниже него.
- **`enabled` под закрытым родителем.** Открыть дочернюю статью, не открыв раздел, нельзя: поле просто не даст того, чего от него ждут.
- **`archivedAt` заполнен, `archivedBy` пуст.** Материал всё равно архивирован: архив определяется по `archivedAt`. Восстанавливать — очисткой обоих полей.
- **`isNew: "true"` в кавычках.** Нужен boolean: строка метку не включит.
- **Цвет без кавычек.** `publicAccentColor: #dc1d51` — `#` начинает комментарий, значение пропадает и подставляется цвет по умолчанию.
- **Оформление портала в конфиге базы.** `portal` читается только из корневого `.knowledge-base/.knowledge.yml`; в базе или разделе поле молча ничего не сделает.
- **Один файл — две темы.** Позже это станет дублем (см. `structure.md`).
- **Относительная ссылка на статью.** Renderer её отбросит — нужен path URL.
- **Аккордеон разорван по строкам.** Открывающий тег должен быть в одной физической строке.

## Что проверить в конкретной базе

Ограничения на имена папок и глубину вложенности: прежде чем создавать третий уровень, посмотри, есть ли он у соседей, и спроси, если ограничение неизвестно.
